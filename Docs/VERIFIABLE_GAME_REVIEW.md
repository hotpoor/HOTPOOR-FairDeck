# 可验证牌局：结合方案讨论稿

状态：方案评审与设计建议，尚未实现，也未确认技术选型。

## 与 HOTPOOR扑克 的结合点

用户希望逐项讨论，重点关注交互形式和数据安全；多种玩法可以作为架构方向，首个玩法仍待选择。

建议分为三个部分：

1. 牌桌交互：拿牌、整理手牌、出牌、翻牌，以及房间、观战和回放体验。
2. 游戏规则：不同玩法分别定义合法操作、公开信息、私密信息和结算规则，并标记版本。
3. 可验证牌局：身份与动作签名、牌局承诺、隐私发牌、证据导出和独立验证。不同玩法可能需要不同证明，不能保证只更换规则就完全复用。

玩家正常操作牌桌；系统在背后生成证据。结算页提供“验证本局”和“导出验证记录”，分别显示已验证、失败、证据不足与未覆盖，不能将未实现的验证显示为通过。

## 原方案需要修正的关键点

- 开局前公开所有随机数，再由公开算法生成整副牌，会让所有参与者推导所有手牌。之后加密保存不能消除已经泄露的信息。
- “无法单独挑选牌序”“局中无法偷看”“事后可验证”是三个不同目标。Commit/Reveal 本身无法同时实现三者。
- 即使共同生成随机数，最后揭示者仍可通过拒绝揭示选择中止。超时、罚款和替代随机数不能直接等同于无偏且可继续的协议；需要另行分析中止和重开行为。
- 哈希承诺只提供对特定数据的绑定能力，不自动证明操作合法；还需要规则验证、签名、顺序、可获取的证据及信任锚。低熵手牌的裸哈希可能被枚举，私密承诺需要合适的随机化设计。
- 服务器先生成明文牌再分别加密，仍然允许服务器看见全部牌。若目标包含运营方不可见，需要研究可验证加密洗牌和受控解密等协议，而非仅增加存储加密。
- 链上记录能提供的保证取决于共识、节点独立性和证据可用性，不能证明写入的内容天然真实。验证节点与参与共识的节点也应区分。
- 赛后公布完整随机种子通常会暴露未亮出的手牌；“复现完整牌局”和“保留弃牌隐私”需要明确取舍或额外密码学证明。
- 这些机制不自动防止玩家串通、终端被控制、拒绝服务或恶意客户端更新。安全承诺必须说明覆盖范围与串通假设。

## 建议推进方式（待确认）

先确定安全目标，再分别验证交互和协议。交互原型可以用测试牌局，但必须明确标为模拟，不能宣称具备密码学安全。

如果目标仅为赛后审计：先研究承诺、签名动作记录与独立验证器，同时明确运营方局中可见的边界，以及赛后手牌公开政策。

如果目标包含运营方局中也看不到全部牌：先做独立的隐私发牌协议原型，验证正确性、非法操作、拒绝参与、串通假设及性能，再接入 Unity。成熟实现和独立安全审查应作为正式安全承诺的前置条件。

联盟链与外部锚定保留接口，等明确需要解决的记录一致性问题后再选型。第一步的签名日志原型不等价于去信任系统。

数据安全还需单独规划密钥保存与恢复、日志脱敏、证据保留期限、回放访问权限和删除范围；永久公开记录只应包含经过评估的最少数据。

## 当前只讨论一个问题

我们是否把“运营方在对局过程中也无法看到所有人的手牌”作为首版必须满足的目标？

这是安全目标选择，不代表已经选定任何具体协议、链或钱包。

## 2026-09-21：安全目标与赛后揭示

已确认的目标（尚未实现）：

- 对局中，即使运营方也不能看到所有玩家的手牌，不能指定发牌结果。公平公正为设计原则，具体保证必须经过协议验证，不能宣称绝对安全已实现。
- 用户提出：整局完全结束后，可以由玩家侧逐个触发合约后呈现手牌。

待澄清：是每位玩家仅能触发公开自己的手牌，还是任何玩家都能逐个触发公开所有人的手牌？尚未确认揭示权限与公开范围。

实现约束建议：结束状态与揭示权限必须由协议验证，不能仅靠界面控制。触发合约不意味着合约天然具备秘密解密能力；具体揭示证据和解密流程仍需设计。暂不选定链、费用机制或强制公开政策。

## 2026-09-21：统一揭秘与离线处理（更新前述待澄清项）

用户明确：本局完全结束后，所有玩家都收到解密请求，各自提交本局解密材料和随机数，通过智能合约协调揭示，方便所有参与者回顾完整牌局。这不是每个人自行选择是否亮牌的模式。对参与者以外的公众是否可见尚未确定。

用户进一步要求：有人离线或不再响应，不能让牌局或赛后揭秘无限卡住；对局期间也应持续检查响应状态，并考虑触发合约。

协议设计约束与待验证点：

- 心跳、带签名响应和合约交互只能证明某个时刻有响应或在截止时间前未响应，无法可靠判断故意离线、网络中断、设备故障或永不返回。状态与处置依据可验证事实，不推断玩家动机。
- 客户端定期提交响应不等于每次都必须发链上交易；心跳频率、链上检查点和超时裁决方式待设计。
- 不能依赖所有玩家赛后自愿再次上线。应在开局前建立并验证可恢复揭示材料，明确恢复参与方、串通阈值、可用性假设与仅在终局后揭示的条件；具体密码学协议未选型，不能仅靠界面禁用提前解密。
- 合约不会凭空恢复缺失秘密。简单公开备用解密材料会破坏局中隐私；仅设置时间戳或超时也不能替代安全恢复协议。
- 不承诺在所有参与者及恢复方都失联、网络或底层链不可用时仍可即时继续。应区分正常完成、超时终止、待恢复验证等状态，明确保证边界。
- 当前“令牌”指本局专用解密份额或材料，不是账号令牌或长期私钥。赛后材料的公开范围以及链上公开性需单独确认。

下一个单独讨论的问题：玩家在对局中超时，应按玩法自动执行预先约定动作继续，还是终止本局并进入揭秘？尚未决定超时时长、扣分或惩罚。

## 2026-09-21：终局规则与四档揭秘权限（以此更新此前统一揭秘设想）

用户明确：合约规则由本局玩家开局前共同确认，不能由运营方临时决定。

- 中止投票门槛可约定为超过半数或至少三分之二，分母为本局全部玩家，开局展示具体票数。
- 是否允许超时自动终局与揭秘也可选；超时的定义、时长仍待讨论。
- 正常结束或按约定中止后，先锁定牌局，再按本局揭秘档位处理。不能边继续对局边揭示全局。
- 终局不等于必须公开所有手牌。此前“统一揭秘”现在被以下四档替代。

用户提出的四档：

| 档位 | 用户表述 | 设计解释 |
| --- | --- | --- |
| 1 | 完全不揭密 | 不新增揭示局中未公开的牌；不会撤回玩家已经看见的内容。是否保存个人历史另行确认。 |
| 2 | 仅对参与者揭秘查询，一个人查询自己 | 终局后，每位参与者只能查询自己的私有牌局记录及原本公开的信息，不能从系统查询他人隐藏牌；参与者自愿汇集各自记录才可拼出全貌。 |
| 3 | 结束后仅对参与者揭秘 | 终局后，每位参与者可查询完整牌局；系统不向局外人开放。 |
| 4 | 结束后完全揭秘公开 | 终局后，完整牌局可对公众查询。 |

第 2 档按赛后查询理解；不改变局中只能获取本人有权看到信息的要求。具体查询记录字段、保存期限尚未确定。

安全边界：

- 权限必须由密钥与协议约束，不能只靠 UI 隐藏。
- 第 1 至 3 档不能在公开链发布足以解开全局的材料；链上证明与私密查询数据分离，具体方案待验证。
- 第 2 档无法强制大家必须线下汇集；玩家可以在线自愿分享自己的信息。第 3 档也无法阻止知情参与者截图或转发。系统权限承诺不等于控制接收者后续行为。
- 所有档位均维持运营方局中不得看到全部手牌的目标。验证功能应说明覆盖范围；不公开隐藏牌时，完整独立验证可能需要额外密码学证明，尚未实现。
- 超时或投票中止不得自动升级揭秘档位。规则在开局前共同确认并绑定本局。
